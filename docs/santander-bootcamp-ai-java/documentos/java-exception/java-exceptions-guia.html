1

O que e uma Excecao?

Uma Excecao (Exception) no Java e um evento anomalo que ocorre durante a execucao do programa (runtime) e interrompe o fluxo normal de instrucoes. Tratar excecoes serve para capturar essas anomalias e permitir que a aplicacao continue rodando de forma estavel.

Excecoes nao sao erros de compilacao — elas ocorrem em tempo de execucao. O compilador so conhece as Checked Exceptions, que ele obriga a tratar antecipadamente.
2

A Hierarquia da Classe Throwable

No Java, todos os tipos de erros e excecoes estendem a classe raiz java.lang.Throwable. Ela se divide em dois ramos principais:

Error — falhas graves no nivel da JVM das quais a aplicacao nao consegue se recuperar (ex: OutOfMemoryError, StackOverflowError). Nao devem ser capturados.

Exception — condicoes de erro previsiveis causadas por falha de logica ou fatores externos. Divide-se em Checked e Unchecked.

3

Checked vs Unchecked Exceptions

A divisao depende da heranca direta da classe RuntimeException.

Checked Exception
// Compilador OBRIGA o tratamento
public void lerArquivo()
        throws IOException {
  Files.readString(
    Path.of("dados.txt"));
}
Unchecked Exception
// Compilador NAO obriga
// Ocorre em runtime
int x = 10 / 0;
// ArithmeticException

String s = null;
s.length();
// NullPointerException

A. Checked Exceptions

Sao todas as classes que estendem Exception, mas que nao estendem RuntimeException (ex: IOException, SQLException).

Regra do compilador: O codigo nao compila sem try-catch ou throws na assinatura do metodo.

Uso sugerido: Erros esperados que dependem de fatores externos fora do controle do seu codigo (abrir um arquivo, falha de conexao de rede).

B. Unchecked Exceptions

Sao todas as classes que estendem RuntimeException (ex: NullPointerException, ArithmeticException).

Regra do compilador: O programa compila mesmo sem try-catch.

Uso sugerido: Erros causados por falhas de programacao ou logica. A melhor pratica e corrigir a logica — nao apenas usar try-catch.

4

Estruturas de Tratamento e Palavras-Chave

O controle de excecoes utiliza cinco blocos e palavras-chave especificas:

try

Delimita o bloco onde a execucao do codigo de risco e monitorada.

catch

Captura a excecao especifica lancada pelo try e executa a logica de contingencia.

finally

Executado sempre apos o try-catch, independente de sucesso ou erro. Ideal para liberar recursos.

throw

Lanca manualmente uma excecao no fluxo: throw new IllegalArgumentException();

throws

Declara na assinatura de um metodo que ele pode propagar uma Checked Exception.

Java 
try {
  // codigo de risco monitorado aqui
  Files.readString(Path.of("dados.txt"));

} catch (FileNotFoundException e) {
  // mais especifico — captura primeiro
  log.error("Arquivo nao encontrado", e);

} catch (IOException e) {
  // mais generico — captura depois
  log.error("Erro de leitura", e);

} finally {
  // sempre executa — libera recursos aqui
}
Ordem dos catch blocks: sempre capture primeiro as excecoes mais especificas (subclasses) e depois as mais genericas (superclasses). Do contrario, o codigo nao compilara por codigo inacessivel.
5

Gerenciamento Automatico de Recursos (Try-with-Resources)

Introduzido no Java 7, resolve o problema de fechar recursos de forma segura sem a verbosidade do finally.

O problema — finally classico

Java — antes do Java 7 
BufferedReader reader = null;
try {
  reader = new BufferedReader(new FileReader("dados.txt"));
  System.out.println(reader.readLine());
} catch (IOException e) {
  System.out.println("Erro: " + e.getMessage());
} finally {
  if (reader != null) {
    try {
      reader.close(); // close() tambem lanca IOException
    } catch (IOException e) {
      System.out.println("Erro ao fechar: " + e.getMessage());
    }
  }
}

A solucao — try-with-resources

Java 7+ 
// O BufferedReader sera fechado automaticamente
try (BufferedReader reader = new BufferedReader(
        new FileReader("dados.txt"))) {

  System.out.println(reader.readLine());

} catch (IOException e) {
  System.out.println("Erro: " + e.getMessage());
}
Exigencia: o recurso precisa implementar a interface AutoCloseable. As classes do proprio Java ja implementam: BufferedReader, Connection, InputStream, PreparedStatement e outras.

Multiplos recursos

Java 
// Recursos fechados na ordem INVERSA da declaracao
try (
  Connection conexao = dataSource.getConnection();
  PreparedStatement stmt = conexao.prepareStatement(
      "SELECT * FROM contas")
) {
  ResultSet rs = stmt.executeQuery();
} catch (SQLException e) {
  throw new RuntimeException("Erro na consulta", e);
}
// stmt fechado primeiro, depois conexao
Pegadinha do OCP — excecao suprimida: se o try lanca uma excecao e o close() tambem lanca, a excecao do close() e suprimida e fica acessivel via e.getSuppressed(). Diferente do finally classico, onde a excecao do finally engolia a do try.
6

Excecoes Customizadas

Quando as excecoes nativas do Java nao expressam o erro de negocio com clareza, crie suas proprias. Imagine que um cliente tenta fazer um Pix e a conta nao existe — o Java lancaria uma NullPointerException ou NoSuchElementException, mensagens que nao dizem nada para quem consome a API.

Java 
// Unchecked — nao exige try-catch em quem chama
public class ContaNaoEncontradaException
        extends RuntimeException {

  public ContaNaoEncontradaException(String id) {
    super("Conta nao encontrada: " + id);
  }
}

// Checked — exige try-catch ou throws em quem chama
public class SaldoInsuficienteException
        extends Exception {

  public SaldoInsuficienteException(double saldo) {
    super("Saldo insuficiente: R$ " + saldo);
  }
}
A escolha entre extends RuntimeException (unchecked) e extends Exception (checked) segue a mesma logica do guia: erro de logica interna = unchecked. Fator externo que quem chama precisa tratar obrigatoriamente = checked.
7

Multi-catch

Introduzido no Java 7, resolve o problema de repetir blocos catch identicos para tipos diferentes de excecao.

Antes do Java 7
try {
  // operacao de risco
} catch (IOException e) {
  log.error(e.getMessage());
} catch (SQLException e) {
  log.error(e.getMessage());
}
Java 7+
try {
  // operacao de risco
} catch (IOException |
         SQLException e) {
  log.error(e.getMessage());
}
Regra do OCP — heranca proibida no multi-catch: voce nao pode combinar excecoes que tem relacao de heranca entre si. FileNotFoundException e subclasse de IOException — isso nao compila:

} catch (IOException | FileNotFoundException e) { }

Capture apenas a mais generica: } catch (IOException e) { }
8

Encadeamento de Excecoes

Resolve um problema critico: nao perder a causa raiz do erro quando voce precisa relancar uma excecao. Sem encadeamento, a causa original some do stack trace.

Errado — causa raiz perdida
try {
  Files.readString(
    Path.of("config.txt"));
} catch (IOException e) {
  throw new RuntimeException(
    "Falha ao carregar");
  // causa original perdida
}
Correto — causa preservada
try {
  Files.readString(
    Path.of("config.txt"));
} catch (IOException e) {
  throw new RuntimeException(
    "Falha ao carregar", e);
  // e = causa original
}

Com encadeamento, o log exibe o stack trace completo:

Stack Trace 
RuntimeException: Falha ao carregar configuracao
    at ServicoConfig.carregar(ServicoConfig.java:22)
Caused by: IOException: config.txt (No such file or directory)
    at Files.readString(Files.java:...)

Aplicacao com excecoes customizadas

Java 
public class FalhaDeTransferenciaException
        extends RuntimeException {

  public FalhaDeTransferenciaException(
          String mensagem, Throwable causa) {
    super(mensagem, causa); // causa original preservada
  }
}

// Uso no Service
try {
  transacaoRepository.save(transacao);
} catch (DataAccessException e) {
  throw new FalhaDeTransferenciaException(
      "Erro ao registrar transferencia Pix", e);
}
// O @ControllerAdvice retorna HTTP 500 limpo
// mas o log preserva o DataAccessException original

A Regra do finally com return — Pegadinha do OCP

O bloco finally sempre executa — e se ele tiver um return, ele sobrescreve qualquer return que estava no try ou no catch.

Java — exemplo basico 
public int calcular() {
  try {
    return 1; // este return e ignorado
  } finally {
    return 2; // sempre retorna 2
  }
}
Java — excecao engolida 
public int calcular() {
  try {
    throw new RuntimeException("erro");
  } finally {
    return 2; // excecao ENGOLIDA silenciosamente
  }
}
// Retorna 2 como se nada tivesse acontecido
Java — variacao mais cobrada no OCP 
public String obterStatus() {
  try {
    return "try";
  } catch (Exception e) {
    return "catch";
  } finally {
    return "finally"; // sempre este
  }
}
  • finally sempre executa — exceto se System.exit() for chamado ou a JVM travar.
  • Se finally tem return, ele sobrescreve qualquer outro return.
  • Se finally tem return, ele engole qualquer excecao em andamento silenciosamente.
  • Boa pratica: nunca coloque return dentro de finally. Use-o apenas para liberar recursos.

O que significa "liberar recursos"

"Liberar recursos" significa fechar ou encerrar qualquer coisa que consome memoria, conexao ou arquivo e que precisa ser finalizada independente do sucesso ou falha da operacao.

Java — liberacao correta de recursos no finally 
Connection conexao = null;
try {
  conexao = dataSource.getConnection();
  // executa operacao no banco
} catch (SQLException e) {
  throw new RuntimeException("Erro na transacao", e);
} finally {
  if (conexao != null) {
    conexao.close(); // libera conexao — sucesso ou falha
  }
}
Hoje o try-with-resources substitui o finally para liberacao de recursos de forma mais segura e legivel. Use finally apenas quando nao puder usar try-with-resources.
10

@ControllerAdvice no Spring Boot

O @ControllerAdvice e uma annotation do Spring Boot que define uma classe como um interceptador global de excecoes. Ele funciona como um ponto central de tratamento de erros para toda a aplicacao — quando qualquer Controller lanca uma excecao que nao foi capturada localmente, o Spring automaticamente redireciona essa excecao para o metodo correspondente dentro da classe anotada.

O nome combina dois conceitos: Controller — porque intercepta excecoes antes que cheguem ao cliente — e Advice — termo da Programacao Orientada a Aspectos (AOP) que significa comportamento aplicado de forma transversal, sem que cada ponto da aplicacao precise conhece-lo.

O problema — sem @ControllerAdvice

Java — try-catch repetido em cada Controller 
@RestController
public class TransferenciaController {

  @PostMapping("/transferir")
  public ResponseEntity<?> transferir(
          @RequestBody TransferenciaRequest request) {
    try {
      servicoTransferencia.transferir(request);
      return ResponseEntity.ok().build();
    } catch (ContaNaoEncontradaException e) {
      return ResponseEntity.status(404).body(e.getMessage());
    } catch (SaldoInsuficienteException e) {
      return ResponseEntity.status(422).body(e.getMessage());
    } catch (RuntimeException e) {
      return ResponseEntity.status(500).body("Erro interno");
    }
  }
}
// Com 10 Controllers, esse try-catch se repete 10 vezes

A solucao — @ControllerAdvice centraliza tudo

Java — handler global 
@ControllerAdvice
public class GlobalExceptionHandler {

  @ExceptionHandler(ContaNaoEncontradaException.class)
  public ResponseEntity<ErroResponse> handleContaNaoEncontrada(
          ContaNaoEncontradaException ex) {
    return ResponseEntity
        .status(404)
        .body(new ErroResponse(404, ex.getMessage(),
            LocalDateTime.now()));
  }

  @ExceptionHandler(SaldoInsuficienteException.class)
  public ResponseEntity<ErroResponse> handleSaldoInsuficiente(
          SaldoInsuficienteException ex) {
    return ResponseEntity
        .status(422)
        .body(new ErroResponse(422, ex.getMessage(),
            LocalDateTime.now()));
  }

  @ExceptionHandler(RuntimeException.class)
  public ResponseEntity<ErroResponse> handleRuntime(
          RuntimeException ex) {
    return ResponseEntity
        .status(500)
        .body(new ErroResponse(500, "Erro interno",
            LocalDateTime.now()));
  }
}

Controller limpo — sem try-catch

Java 
@RestController
public class TransferenciaController {

  @PostMapping("/transferir")
  public ResponseEntity<?> transferir(
          @RequestBody TransferenciaRequest request) {
    servicoTransferencia.transferir(request);
    return ResponseEntity.ok().build();
    // excecoes sobem automaticamente para GlobalExceptionHandler
  }
}

Corpo de erro padronizado — ErroResponse com Record Java 21

Java 21 — Record 
public record ErroResponse(
  int status,
  String mensagem,
  LocalDateTime timestamp
) {}
JSON — resposta padronizada 
{
  "status": 404,
  "mensagem": "Conta nao encontrada: CPF-001",
  "timestamp": "2026-06-12T14:30:00"
}

Como o fluxo funciona

O @ControllerAdvice captura excecoes especificas antes das genericas — a mesma regra de ordem dos catch blocks. O ErroResponse usa Record do Java 21 — imutavel e sem boilerplate.
11

Regra Pratica — Resumo

Tipo Obrigatorio tratar (try/catch) ou declarar (throws)? Quando usar
Error Nao Falhas graves da JVM — nao capturar
RuntimeException e subclasses Nao Erros de programacao — corrigir a logica
Outras subclasses de Exception Sim Fatores externos previsiveis — arquivo, rede, banco
Excecoes Customizadas Unchecked Nao Regras de negocio — ContaNaoEncontradaException

Boas Praticas Consolidadas

  • Capture sempre a excecao mais especifica possivel — nunca catch (Exception e) ou catch (Throwable t) de forma generica.
  • Ordene os blocos catch do mais especifico para o mais generico.
  • Nunca silencie excecoes com blocos catch vazios.
  • Use try-with-resources sempre que trabalhar com recursos que implementam AutoCloseable.
  • Preserve a causa raiz ao relancar — sempre passe o Throwable original no segundo argumento.
  • Crie excecoes customizadas para expressar erros de negocio com clareza.
  • Nunca coloque return dentro de finally.
  • Centralize o tratamento de excecoes no Spring Boot com @ControllerAdvice.
Java 17 vs Java 21: ambas as versoes tem o mesmo comportamento de excecoes. Nao ha mudancas de linguagem nessa area entre as duas versoes — este guia se aplica a ambos os contextos sem ajuste.
