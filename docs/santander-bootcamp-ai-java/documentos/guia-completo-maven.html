1. Introdução ao Apache Maven

O Apache Maven é uma ferramenta de automação de compilação (build) e gerenciamento de dependências. Ele centraliza o processo de ciclo de vida do desenvolvimento de aplicações Java. Suas principais responsabilidades são:

  • Gerenciamento de dependências: Download e atualização de bibliotecas externas a partir de repositórios remotos (como o Maven Central).
  • Repositório Local (pasta .m2): Salvar as bibliotecas baixadas no diretório local da máquina (C:\Users\Usuario\.m2\repository) para reutilização futura sem a necessidade de novos downloads.
  • Padronização de diretórios: Definição de uma estrutura unificada de pastas compartilhada por todos os projetos Maven.

2. Estrutura de Diretórios Padrão

O Maven adota a filosofia de "Convenção sobre Configuração", determinando uma árvore de diretórios fixa:

meu-projeto/
├── pom.xml                      <-- Configuração principal do Maven
├── src/
│   ├── main/
│   │   ├── java/                <-- Código-fonte Java do sistema (.java)
│   │   └── resources/           <-- Arquivos de propriedades e configurações (.yml, .properties, .xml)
│   └── test/
│       ├── java/                <-- Classes de testes automatizados (ex: JUnit)
│       └── resources/           <-- Configurações exclusivas do ambiente de testes

3. Anatomia Detalhada do Arquivo pom.xml

O pom.xml (Project Object Model) é um arquivo estruturado em formato XML. Abaixo são explicados os principais blocos e suas respectivas tags.

3.1. Coordenadas do Projeto (GAV)

Servem para identificar de forma única o projeto dentro do ecossistema de bibliotecas do Java:

  • <groupId>: Organização ou empresa dona do projeto. Segue a estrutura reversa de domínio de internet (ex: com.santander).
  • <artifactId>: Nome do projeto ou do módulo de software gerado (ex: exemplo-maven).
  • <version>: A versão do projeto.
    • SNAPSHOT (ex: 1.0.0-SNAPSHOT): Indica versão em desenvolvimento ativo. O Maven atualizará os binários sempre que houver novo build.
    • Release (ex: 1.0.0): Indica versão final, estável e imutável.
  • <packaging>: Tipo de arquivo a ser gerado (ex: jar para console/APIs ou war para aplicações web corporativas).

3.2. A Estrutura do Bloco de Dependências

O bloco <dependencies> gerencia a importação de bibliotecas externas de forma automática:

<dependencies>
    <dependency>
        <groupId>org.postgresql</groupId>
        <artifactId>postgresql</artifactId>
        <version>42.7.1</version>
        <scope>runtime</scope>
        <type>jar</type>
        <optional>false</optional>
        <exclusions>
            <exclusion>
                <groupId>org.slf4j</groupId>
                <artifactId>slf4j-simple</artifactId>
            </exclusion>
        </exclusions>
    </dependency>
</dependencies>

Explicação das Tags Internas da Dependência:

  • <groupId> e <artifactId>: Coordenadas que localizam a biblioteca desejada.
  • <version>: Versão exata a ser baixada.
  • <scope>: Define a visibilidade da dependência no ciclo de vida (ver detalhes na seção 4).
  • <type>: Formato de empacotamento da biblioteca (geralmente jar).
  • <optional>: Se definido como true, impede que outros projetos herdem esta biblioteca indiretamente (evitando dependências transitivas indesejadas).
  • <exclusions>: Usado para bloquear dependências transitivas indesejadas trazidas automaticamente pela biblioteca externa.

4. Escopos de Dependências (Scope)

Controlam em quais fases do projeto a dependência é adicionada ao Classpath:

  • compile (Padrão): A dependência fica disponível na compilação, testes e execução do sistema. É empacotada no artefato final.
  • test: Disponível apenas para compilar e rodar testes da pasta src/test/java (ex: JUnit). Não vai para a produção.
  • provided: Usada na compilação, mas omitida no empacotamento final porque o servidor web de execução já fornece essa biblioteca nativamente.
  • runtime: Desnecessária para compilar, mas exigida para a execução do sistema (ex: drivers JDBC).

5. Herança de Configurações com a Tag Parent

A tag <parent> permite reutilizar definições de um projeto pai (Parent POM) para simplificar a configuração de projetos filhos:

<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.2.0</version>
    <relativePath/>
</parent>

O POM filho herda automaticamente as propriedades, versões recomendadas, catalogações de plugins e dependências básicas do pai.

Regra de Sobrescrita: O projeto filho tem prioridade absoluta. Se declarar uma propriedade com o mesmo nome da propriedade do pai (ex: <java.version>21</java.version>), o valor do filho sobrescreverá a configuração herdada do pai.

6. Tags Avançadas do pom.xml

  • <dependencyManagement>: Declara dependências e suas versões no projeto pai para que os filhos apenas referenciem o groupId e artifactId sem a necessidade de reescrever a versão, garantindo alinhamento e consistência de versões.
  • <pluginManagement>: Mesma funcionalidade do gerenciamento de dependências, mas focada na padronização de plugins de build.
  • <modules>: Lista os subdiretórios pertencentes ao projeto principal em estruturas multimódulos.
  • <repositories>: Adiciona servidores de dependência externos alternativos ao Maven Central.
  • <distributionManagement>: Configura o endereço IP ou a URL do servidor interno onde o JAR gerado pelo build deve ser publicado (Nexus, Artifactory, etc.).
  • <profiles>: Permite criar configurações que variam de acordo com o ambiente (ex: desenvolvimento, homologação e produção).

7. Ciclo de Vida do Build e Comandos Úteis

O ciclo de vida do Maven é dividido em fases sequenciais executadas a partir do terminal:

Comando Descrição e Ação Realizada
mvn clean Apaga a pasta temporária de compilação (target/), limpando builds antigos.
mvn compile Compila todos os códigos Java principais na pasta src/main/java.
mvn test Compila e executa todos os testes de JUnit na pasta src/test/java.
mvn package Executa testes e empacota o código em formato de distribuição (gerando o arquivo .jar ou .war).
mvn install Gera o pacote e o publica no repositório local (pasta .m2) para que outros projetos locais possam utilizá-lo.
mvn deploy Publica a versão estável final do JAR no repositório remoto corporativo configurado.
