Introdução ao SOLID

SOLID é um acrônimo criado por Michael Feathers e popularizado por Robert C. Martin (Uncle Bob) que consolida cinco princípios de design de software orientado a objetos. O objetivo principal da aplicação do SOLID é criar sistemas fáceis de manter, estender, testar e refatorar ao longo do tempo.

S - Single Responsibility Principle (Princípio da Responsabilidade Única)

Definição: Uma classe deve ter uma, e apenas uma, razão para ser modificada. Isso significa que ela deve possuir apenas uma única responsabilidade ou papel dentro do sistema.

Código Incorreto (Violando o SRP):

A classe Pedido acumula dados do negócio, lógica de persistência e geração de impressão, gerando acoplamento excessivo:

public class Pedido {
    public void calcularTotal() { /* cálculo */ }
    public void salvarBancoDados() { /* acesso ao banco */ }
    public void enviarEmailConfirmacao() { /* lógica de e-mail */ }
}
Código Correto (Aplicando o SRP):

Dividimos as responsabilidades em classes distintas com coesão máxima:

public class Pedido {
    public void calcularTotal() { /* cálculo */ }
}

public class PedidoRepository {
    public void salvar(Pedido pedido) { /* acesso ao banco */ }
}

public class EmailService {
    public void enviarConfirmacao(Pedido pedido) { /* lógica de e-mail */ }
}

O - Open/Closed Principle (Princípio Aberto/Fechado)

Definição: Entidades de software (classes, módulos, funções) devem estar abertas para extensão, mas fechadas para modificação. Novos comportamentos devem ser adicionados criando novas classes, não alterando as existentes.

Código Incorreto (Violando o OCP):

Toda vez que um novo meio de pagamento for adicionado, a classe existente precisará ser modificada, correndo o risco de quebrar regras de negócio já homologadas:

public class ProcessadorPagamento {
    public void processar(String tipo, double valor) {
        if (tipo.equals("Cartao")) { /* processa cartao */ }
        else if (tipo.equals("Boleto")) { /* processa boleto */ }
    }
}
Código Correto (Aplicando o OCP):

Usamos polimorfismo. A classe processadora depende de uma interface, permitindo novos meios de pagamento sem alterar códigos antigos:

public interface MeioPagamento {
    void pagar(double valor);
}

public class PagamentoBoleto implements MeioPagamento {
    public void pagar(double valor) { /* lógica boleto */ }
}

public class ProcessadorPagamento {
    public void processar(MeioPagamento meio, double valor) {
        meio.pagar(valor);
    }
}

L - Liskov Substitution Principle (Princípio da Substituição de Liskov)

Definição: Uma classe derivada (filha) deve ser substituível por sua classe base (pai) sem alterar o funcionamento correto do programa.

Código Incorreto (Violando o LSP):

A classe ContaPoupanca herda de Conta, mas lança uma exceção no método renderJuros() por não fazer sentido para esse tipo de conta, quebrando a expectativa do programa ao interagir com a superclasse:

public class Conta {
    public void renderJuros() { /* lógica */ }
}

public class ContaPoupanca extends Conta {
    @Override
    public void renderJuros() {
        throw new UnsupportedOperationException("Poupança não rende juros dessa forma.");
    }
}
Código Correto (Aplicando o LSP):

Refatoramos a hierarquia para que a herança seja conceitualmente correta:

public class Conta {
    // Métodos comuns a todas as contas
}

public class ContaRendimento extends Conta {
    public void renderJuros() { /* lógica */ }
}

public class ContaPoupanca extends ContaRendimento {
    @Override
    public void renderJuros() { /* cálculo específico */ }
}

I - Interface Segregation Principle (Princípio da Segregação de Interfaces)

Definição: Uma classe cliente não deve ser forçada a depender de métodos de uma interface que ela não utiliza. É preferível criar várias interfaces pequenas e específicas do que uma única interface genérica.

Código Incorreto (Violando o ISP):

Uma classe que representa um funcionário terceirizado é obrigada a implementar o método receberBeneficios() de forma vazia ou retornando erro:

public interface ContratoTrabalho {
    void baterPonto();
    void receberBeneficios();
}

public class Terceirizado implements ContratoTrabalho {
    public void baterPonto() { /* marca ponto */ }
    public void receberBeneficios() {
        // Terceirizados não recebem benefícios da empresa contratante
        throw new UnsupportedOperationException();
    }
}
Código Correto (Aplicando o ISP):

Segregamos a interface em contratos menores e mais focados:

public interface RegistroPonto {
    void baterPonto();
}

public interface BeneficiosEmpresa {
    void receberBeneficios();
}

public class Terceirizado implements RegistroPonto {
    public void baterPonto() { /* marca ponto */ }
}

public class Efetivo implements RegistroPonto, BeneficiosEmpresa {
    public void baterPonto() { /* marca ponto */ }
    public void receberBeneficios() { /* recebe benefícios */ }
}

D - Dependency Inversion Principle (Princípio da Inversão de Dependência)

Definição: Módulos de alto nível não devem depender de módulos de baixo nível. Ambos devem depender de abstrações (interfaces). Abstrações não devem depender de detalhes; detalhes devem depender de abstrações.

Código Incorreto (Violando o DIP):

A classe Interruptor possui acoplamento rígido com a classe física Lampada. Se precisarmos acionar outro dispositivo, a classe precisará ser refeita:

public class Lampada {
    public void ligar() { /* liga */ }
}

public class Interruptor {
    private Lampada lampada;
    public Interruptor() {
        this.lampada = new Lampada(); // Acoplamento forte
    }
    public void acionar() {
        lampada.ligar();
    }
}
Código Correto (Aplicando o DIP):

Criamos uma interface intermediária. O interruptor agora controla qualquer classe que implemente DispositivoLigar:

public interface DispositivoLigar {
    void ligar();
}

public class Lampada implements DispositivoLigar {
    public void ligar() { /* liga */ }
}

public class Interruptor {
    private DispositivoLigar dispositivo;
    // O dispositivo é injetado via construtor, dependendo apenas da interface
    public Interruptor(DispositivoLigar dispositivo) {
        this.dispositivo = dispositivo;
    }
    public void acionar() {
        dispositivo.ligar();
    }
}
