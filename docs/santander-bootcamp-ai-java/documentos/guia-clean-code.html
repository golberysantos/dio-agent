☕ Guia de Estudo: Princípios de Clean Code (Código Limpo)

Este documento reúne as principais regras conceituais e práticas de Clean Code, baseadas na literatura de engenharia de software de Robert C. Martin. Ele serve como material didático e conteúdo de referência para codificação profissional em Java.

1. Nomes Significativos

Nomes de variáveis, métodos e classes devem revelar sua intenção sem a necessidade de comentários secundários.

  • Use nomes pronunciáveis e fáceis de buscar: Evite abreviações e letras isoladas (com exceção de contadores simples em laços de repetição).
  • Nomes de classes: Devem ser substantivos ou frases com substantivos (ex: Usuario, ProcessadorPedido), nunca verbos.
  • Nomes de métodos: Devem conter verbos ou frases verbais (ex: calcularDesconto(), salvar()).
Exemplo Comparativo:
// Incorreto (Sem significado claro):
int d; // dias decorridos
int f; // flag de status
public void proc() { /* ... */ }

// Correto (Autodocumentado):
int diasDecorridos;
int statusDoCadastro;
public void processarPedido() { /* ... */ }

2. Funções e Métodos Pequenos

O tamanho e o foco de um método determinam sua legibilidade. As regras fundamentais são:

  • Devem ser curtas: Um método idealmente deve possuir poucas linhas de código. Se ultrapassar de 15 a 20 linhas, provavelmente está realizando tarefas que deveriam ser isoladas.
  • Fazer apenas uma coisa (Single Responsibility): O método deve realizar exatamente uma ação e fazê-la bem.
  • Poucos argumentos: A quantidade ideal de argumentos para uma função é zero (niládica), seguida por um (monádica) e dois (diádica). Evite funções com três ou mais argumentos; nesses casos, agrupe os dados em uma classe de parâmetros.
Exemplo de Refatoração (Método Multifunção vs. Métodos Focados):
// Incorreto (Faz muitas coisas: calcula, valida e atualiza status):
public void processarPagamento(double valor, String cartao, String titular, String cvv) {
    if (valor <= 0) {
        throw new IllegalArgumentException("Valor inválido");
    }
    // Lógica complexa de cobrança da operadora de cartão
    // Lógica de atualização de status do banco de dados
}

// Correto (Dividido em ações atômicas):
public void processarPagamento(PagamentoDados dados) {
    validarValor(dados.getValor());
    cobrarOperadora(dados.getCartao(), dados.getValor());
    atualizarStatusPagamento(dados.getPedidoId());
}

3. Regras de Comentários

O uso de comentários deve ser visto como uma falha na expressividade do código. O objetivo principal é escrever um código tão limpo que os comentários se tornem redundantes.

  • Comentários ruins: Aqueles que explicam "o que" o código está fazendo, repetindo o que a própria linha já diz.
  • Comentários aceitáveis: Explicações de intenções por trás de decisões arquiteturais (o "porquê" de usar determinada técnica) ou alertas de consequências de uso.
  • Código comentado: Nunca deixe código comentado no repositório. Ele polui o arquivo e cria dúvidas para outros desenvolvedores. Remova-o; o histórico de alterações (Git) serve para recuperar códigos antigos se necessário.
Exemplo Comparativo:
// Incorreto (Comentário redundante):
// Verifica se o funcionário é elegível para promoção
if (funcionario.getTempoServico() > 2 && funcionario.getAvaliacao() == Status.EXCELENTE) {
    // ...
}

// Correto (O código se explica sozinho):
if (funcionario.isElegivelParaPromocao()) {
    // ...
}

4. Tratamento de Erros Limpo

A forma como gerenciamos falhas dita a robustez da aplicação. As regras para tratamento de erros são:

  • Use exceções em vez de códigos de retorno: Códigos de erro forçam o chamador a validar o resultado imediatamente, poluindo o fluxo principal do algoritmo. Exceções separam a lógica de sucesso da lógica de erro.
  • Não retorne e não passe Null: Retornar nulo força validações excessivas de if (objeto != null) para evitar `NullPointerException`. Em vez disso, retorne uma lista vazia, lance uma exceção apropriada ou use a classe Optional (Java 8+).

5. Princípio DRY (Don't Repeat Yourself)

Evite duplicar regras de negócio ou trechos de algoritmos idênticos em partes diferentes do sistema. A duplicação dificulta a manutenção, pois qualquer correção de bug exigirá alterações em múltiplos arquivos. Centralize a lógica comum em classes ou métodos utilitários reutilizáveis.
